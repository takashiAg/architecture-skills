# 決定論的に保証すべき境界

## 「決定論的」の対象

同じ正規化入力、同じ状態・ルールversionなら、同じ判断を返す処理を指す。時刻、乱数、外部応答、並行更新は入力や依存として明示し、結果を追跡できるようにする。すべてをpureにすることや、分散システム全体が常に再現可能という意味ではない。

「AIでコードを書く」ことと「本番の判断を毎回AIにさせる」ことは違う。AIが実装した計算関数でも、検証された式とテストで動けば決定論的に運用できる。

| 処理 | 担当 | AIを使うなら |
| --- | --- | --- |
| 合計、税、丸め、単位・日付変換 | 明示した規則によるコード | 入力の抽出候補まで |
| schema、enum、必須項目、範囲 | parserとvalidator | 曖昧文から構造化候補を作る |
| 認証・権限・tenant・所有権 | trusted identityとpolicy engine／コード | 許可の根拠にしない |
| 業務の状態遷移・不変条件 | domain関数と保存時の制約 | 操作候補のみ |
| ID解決・実在確認 | 許可されたDB/API照合 | 名前候補の抽出のみ |
| 一意性・重複排除・冪等性 | DB制約、key、transaction | promptの「二度行わない」に任せない |
| build・型・lint・test合否 | 実コマンド、exit code、検証器 | 失敗の説明と修正案 |
| 形式変換・定型rename | parser、AST、codemod等 | 変換ルールの提案 |
| 要約・意図抽出・曖昧な分類 | LLM等の候補生成 | 評価・棄却・fallbackを設計 |
| 必ず同じ手順の実行 | workflow／state machine | 手順選択まで動的にする根拠があるか検討 |

金融計算の例では、整数の最小通貨単位やdecimal等の表現と丸め規則まで決める。浮動小数点誤差を残したまま「AIを外したから正しい」としない。

## 推奨する境界

```text
曖昧な入力
  → LLMで候補抽出
  → schema検証
  → 実在情報・権限・業務制約との照合
  → 許可された操作をコードで実行
  → 結果と操作IDを記録
```

抽出された金額は事実確定ではない。原文や信頼できる台帳との照合が必要な用途では確認する。信頼度スコアをLLMが自己申告しただけで高信頼と扱わない。

例: 請求書の行項目をAIで抽出し、コードで合計を再計算して原文の総額と照合する。tenantと支払権限は認証済みidentityで確認する。不一致は棄却／要確認へ進め、LLMに整合する数字を作らせて支払いを続けない。

DDD構成なら、LLM clientはoutbound、利用するポートはapplication、確定した業務ルールはdomain、形式変換は境界へ置く。domainの決定を直接LLMに依存させない。

## 重大なアンチパターン

- promptだけで管理者判定・支払上限・状態遷移を守っている。
- AIにSQL／shell／tool引数を作らせ、対象や権限を検証せず実行する。
- schemaに合うJSONだから内容も真実とみなす。構造と意味は別に検証する。
- temperature=0、seed、model ID固定だけで完全再現性があるとする。
- 再試行で成功応答が出るまで課金・作成・送信を繰り返す。
- testの失敗をAIの「問題なし」で通す、または都合よく期待値を緩める。
- 手順が固定なのにagentに毎回選ばせ、抜けた工程を検出できない。

LLMのtool呼び出しは要求として受け取り、実行側でschema、allowlist、権限、現在状態を確認する。ユーザー文書や検索結果の指示を実行権限に昇格させない。Googleのfunction callingも、モデルが提案する呼び出しとアプリ側の実行を区別している。[公式ガイド](https://ai.google.dev/gemini-api/docs/function-calling)

## 再試行と記録

timeout時に副作用が成功済みか不明な場合は、操作IDで照会する。冪等keyを再試行のたびに作り直さない。同じ要求の重複、同時実行、部分失敗を扱い、「exactly once」を根拠なく保証しない。

モデルID、prompt/schema/tool version、必要な入力の参照、設定、検証結果、操作IDを記録する。ログへ秘密や全文を無条件保存しない。固定fixtureによるコードのテストと、実モデルの変動を測る評価を分ける。

## 修正の優先度

権限迂回・誤った金額・二重更新が起きる経路を最優先。次にデータの誤確定や復旧不能な処理。最後に費用・遅延・文章品質を改善する。重大度は実際の到達経路と検証の有無で決める。

境界値、誤ったID、権限なし、重複、並行実行、途中失敗、モデルtimeout／拒否／壊れた出力を対象に、コード側の不変条件を確認する。悪い入力を良い入力へ勝手に修正して検証を通さない。
