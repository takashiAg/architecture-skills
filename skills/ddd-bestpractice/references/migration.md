# DDDへの段階的移行

目標をフォルダ整理でなく「注文ルールを一か所で守る」「HTTPなしで検証する」と定義する。小さな接続点から置き換える。[Strangler Fig](https://martinfowler.com/bliki/StranglerFigApplication.html)

業務ルールがあり入口と保存先を追えるユースケースを一つ選ぶ。全Entity／repositoryの一括移動から始めない。CRUDだけなら境界整理で止めてもよい。

| 段階 | 変更 | 検証 | 戻し方 |
| --- | --- | --- | --- |
| 現状把握 | 公開契約、ルール、保存条件を記録 | 成功・失敗・権限・副作用 | 変更なし |
| 特性テスト | 観測可能な既存動作を固定 | 現行で再現。既知の不具合は別記 | テスト追加を独立扱い |
| ユースケース抽出 | 入口からapplicationへ | 公開契約の維持 | 呼び先を戻す |
| 判断の抽出 | domainにルールを移す | DBなしで不変条件・異常系 | 対象変更を戻す |
| 依存隔離 | ポートとoutbound | 実DBの結果・transaction・競合 | 互換な旧adapterへ |
| 切り替え | bootstrapで配線 | 契約、エラー率、業務指標 | 互換な旧経路へ |
| 定着 | 旧経路削除とimport制約 | 利用者・運用の依存が残らない | 検証済みリリース再配備 |

既存の接続点があれば活用し、無意味な中間層を作らない。振る舞い変更は配置変更と区別する。

新applicationの契約をoutboundで旧サービス／スキーマへ変換する。旧モデルを新domainへ持ち込まない。新旧比較は読み取りや副作用のない計算で行い、課金・メール・書き込みを二重実行しない。

配置変更とDB変更を分ける。DB変更が必要なら互換形式の追加→backfill→新旧互換期間→切替→旧形式削除を具体化する。旧コードが新データを読めるか確認し、不可逆な変換後にGit revertだけで復旧できるとしない。

複数contextのtransactionが必要なら境界を再検討する。分散基盤を自動導入しない。必要ならoutboxを業務更新と同一transactionにし、consumerの重複実行も扱う。

対象ユースケースの契約とルールが検証され、内側に実装依存がなく、配線と戻し方が説明できれば一区切り。リポジトリ全体のDDD化やmonorepo化を完了条件にしない。実装依頼なら計画だけで止めず変更と検証を完了する。
