# 構成レビューとアンチパターン

入口から業務判断、保存、応答まで追い、失敗・同時実行・再試行の条件を調べる。`services/` がユースケース、`repositories/` がDB実装を担い、依存が正しければ名前だけで欠陥にしない。

現在のパス、読んだ関数／import、実際の責務、維持／分割／移動／未確認、改善効果を表にする。木構造だけで「DDD準拠」と断定しない。

## 調査候補

| 兆候 | 確認する実害 | 最小の対処 |
| --- | --- | --- |
| domainがORM/HTTP/SDKをimport | 型、基底class、decoratorまで技術に依存 | adapterで変換 |
| applicationが具体storeをnew | DBなしで実行できない。配線が混在 | 利用側ポートと注入 |
| controllerに業務ルール | CLIやジョブ経由で迂回できる | domainの操作に集約 |
| Entityがsetterのみ | ルール散在。CRUDや関数型モデルとは区別 | 意味のある状態遷移 |
| 巨大集約 | 不要なロード・競合・transaction | 不変条件で境界再検討 |
| table単位repository | 子だけ更新して集約の条件を破る | root経由の更新口 |
| sharedに全モデル | contextの異なる意味・変更周期が結合 | モデルを分け境界で変換 |
| app同士の相対import | 配備単位が内部構造に結合 | 共有すべき機能だけpackage化 |
| 巨大barrel・循環 | domain参照でadapterまで引かれる | 公開口の分離と依存逆転 |
| 何でもinterface・基底class | 未使用の抽象化、多段委譲 | 外部境界を残して簡素化 |
| 保存後の必須通知 | 失われる通知、二重送信 | 必要な配信保証と冪等性 |
| domain内の事前チェックのみ | 並行要求が両方条件を通過 | 保存時の条件付き更新 |
| queryが巨大集約を復元 | 不要なロードや副作用 | queryポートとDTO |
| clientのtenantを信用 | 別利用者のデータへ到達 | 検証済みactorと権限確認 |

貧血モデルは業務ルールを外へ散らすコストとして評価する。classの数は品質指標にしない。[Anemic Domain Model](https://martinfowler.com/bliki/AnemicDomainModel.html)

## 報告

高: 現実的な操作で不整合・不変条件違反・権限迂回が起きる。中: 現在の変更波及やテスト困難に根拠がある。提案: 将来の分割や命名整理。

各指摘は「重要度／ファイル:行／発生条件／影響／最小の修正／確認方法」。未確認事項を欠陥として数えない。問題がない範囲と調査していない範囲も示す。

## 修正後の検証

- domain: 不正な状態遷移、境界値。
- application: fakeのポートで失敗時も含むユースケースの結果。
- outbound: 必要な実DB等で変換、制約、transaction、競合。
- inbound: 入力、認証情報、エラーと公開契約。
- import制約: 新規の境界違反を検出できること。

ファイル名一致だけのテストや内部呼び出しを固定するモックを増やさず、実害に対応する最小の検証を選ぶ。
